# Frontend — מעקב UX פתוח

**מצב: רשימת העבודה סונכרנה עם מודל המסמך היחיד ועם הקוד ב־2026-09-29.**

רשימת עבודה, לא חוזה. המפרטים המחייבים ב־[`../spec/`](../spec/) גוברים: שינוי
בזרימה, בהרשאות או במשמעות מצב חייב להתאים להם, וסתירה לא פתורה היא חסם.
תיעוד המימוש של המשימות שנסגרו נמצא בקוד ובבדיקות; הפירוט שלהן הוסר מכאן ונשמר
ב־Git history. UX-14 ו־UX-15 אינם ברשימה; המספור המקורי נשמר.

## מה נשאר

קבלה חיה ואיכות הניסוח מתועדות ב־[דוח הקבלה](acceptance/2026-09-29.md).
אין להמיר אוטומטית משימה מהמודל הישן לדרישת מוצר חדשה.

- **UX-08 — ממומש:** החיפוש כולל מועמדויות, עובדות והיסטוריית עובדות; „כל התוצאות”
  מעביר את המונח לרשימת המועמדויות. הכיסוי ב־`GlobalSearch.test.tsx` כולל יותר משמונה
  תוצאות, קישור לעובדה וקישור לאירוע. אין כאן חיפוש בטיוטות היסטוריות שאינן נשמרות.
- **UX-17 — הוחלף בהחלטת מוצר:** אין עוד `RevisionPage` או רשומות ApprovedRevision.
  [מודל המסמך היחיד](decisions/single-document-model.md) שומר מסמך משתנה והגשות
  בלתי־משתנות. אין לממש מחדש היסטוריית אישורים שלא נשלחו. אם נדרשת השוואת הגשות,
  יש להגדיר אותה מול רשומות Submission, ולא מול גרסאות שאינן קיימות.
- **בירור ניסוח שנדחה — ממומש:** דוח הפעולה מציג את המשפט, ההקשר והמקורות שנבדקו,
  ומקשר לתיקון השורה או למחזור העובדה. אין מסלול לאישור חריגה מהעובדות.
- **אישור והפקת PDF — ממומש:** בדיקה בעורך, אישור מפורש ורינדור אוטומטי בעקבותיו.

### UX-09 - ממומש;

ב־[`JobPostingUpdate`](../frontend/src/features/application-detail/components/JobPostingUpdate.tsx) קיימים ולידציית URL משותפת, מניעת שליחה ללא שינוי בטקסט ובכתובת, שליחת טקסט המשרה ללא `trim`, הסבר על יצירת תצלום חדש ושמירת הקודם, ושימור הקלט והצגת שגיאה בכשל שמירה.

**תרחישי קבלה שהרצתם לא אומתה:** URL תקין, שגוי וריק; ללא שינוי; שינוי URL בלבד; שינוי טקסט בלבד, כולל רווחים; כשל שרת ורענון הקשר.

## ניסיונות חוזרים

שליחה חוזרת של אותו מפתח היא אותה פעולה. ניסיון חדש נעשה ב־`retry_operation`,
שיוצר Operation חדש ומחזיר את הממשק לצפייה בו; המפתח הבא נגזר מהמזהה החדש.
זו ההתנהגות של `OperationActions` ושל state-and-use-cases §19, ולא כשל קבוע
שחייבים לעקוף באמצעות החלפת מפתח בעת רינדור React.

## כללי עבודה וסגירה

- **P1 — עדיפות גבוהה:** תהליך הכנת קורות החיים ושימוש יומיומי במסמך.
- **P2 — שיפור:** נוחות, חיפוש ואחידות ממשק.
- **P0 — חסם תהליך:** דרך מפורשת לפתרון החלטות שחוסמות אישור; יש לטפל לפני שיפורי נוחות.
- לפני מימוש מאמתים את הפער בקוד ובתרחיש שימוש. אם הוא כבר מכוסה, מתעדים את הכיסוי וסוגרים בלי לממש מחדש.
- הרשימה אינה אישור לשינוי חוזי המוצר. שינוי בזרימה, בהרשאות או במשמעות מצב חייב להתאים למפרט; סתירה לא פתורה היא חסם.
- React פונה ל־FastAPI; לוגיקת שימוש והרשאות נשארת בשכבת היישום. ה־API אינו מתחיל עבודת רקע בעצמו.
- אין לדרוס עובדות קנוניות, JobSnapshot, עדות ספק או רשומת הגשה קיימת במסגרת שיפורי UX. המסמך המשתנה כפוף לחוזי העריכה והכשירות.
